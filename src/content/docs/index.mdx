## “We get the whole order back, right?”

</header>
<img class="dim-scene" src="/dido/order-id.webp" width="640" height="374" alt="" loading="lazy" />
<div class="dim-example-body">

This time Dido asks. His architect shakes her head. “Just the ID.” They pull up **Web App → API** and write that down. Now Dido can give his agent a file that says exactly what goes out (`Cart`) and what comes back (`OrderId`).

```dim title="shop.dim"
sendCart: web.checkout -> api.checkout "Send cart" {
  op call;
  data push api.orders.cart;
  data pull api.orders.orderId;
}
```

## “Which way is that data going?”

</header>
<img class="dim-scene" src="/dido/missing-direction.webp" width="640" height="330" alt="" loading="lazy" />
<div class="dim-example-body">

Dido wrote down the request type. He left out who sends it. CI flags the missing direction with `E406`. The web app sends the request, so Dido adds `push`.

```diff
- data api.orders.cart;
+ data push api.orders.cart;
```

### When the system gets bigger

- Define [elements](/menulis/elemen/) and [relations](/menulis/relasi/), then describe [HTTP contracts](/konsep/endpoint/) or [code details](/konsep/level-kode/) where needed.
- Use a [flow](/konsep/alur/) to follow a sequence such as checkout or refunds.

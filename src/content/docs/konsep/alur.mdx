A reviewer wants to know when payment is charged before the order is saved, and what happens if the charge is declined. Arrange the checkout relation ids as flow steps, then separate the success path from the failure path.

Arrows on the map answer "who talks to whom". The next question is usually "what happens when the shopper clicks pay?". The answer is a **sequence** of relations, and a `flow` stores that sequence in the model.

```dim
flow checkout "Checkout" {
  description "From the shopper clicking pay to the order being saved.";
  step clickPay;
  step postCheckout;
  step runCheckout;
  step computeTotal;
  step charge "Charge first";
  step chargeGateway;
  alt {
    case paid "Payment succeeded" {
      step saveOrder "Save once charged";
      step insertOrder;
    }
    case declined "Payment declined" {
      step showDeclined;
    }
  }
}
```

Each `step` refers to a relation by its id. A step's note is optional; without one, the relation's label is used.

## Branches

Real journeys branch. A flow has three kinds of branch, and every branch must have an id and a label:

| Block | Meaning | Example |
|---|---|---|
| `alt` | exactly one of several paths | payment succeeds or is declined |
| `opt` | steps that may be skipped | using a coupon |
| `par` | paths that run at the same time | sending a receipt and writing an audit log |

```dim
opt coupon "Use a coupon" {
  step validateCoupon;
}

par {
  lane receipt "Send receipt" { step sendReceipt; }
  lane audit "Write audit log" { step writeAudit; }
}
```

`alt` and `par` need at least two branches, and every branch needs at least one step. Branches can nest.

## Numbering

Steps are numbered so they're easy to refer to in discussion. The main path is numbered 1, 2, 3, …. A branch block takes one number, and each of its branches gets a letter. In the checkout flow above, `chargeGateway` is step 6, `insertOrder` is 7a.2, and `showDeclined` is 7b.1.

## Flows at each zoom level

A flow is written at the most detailed level, like relations. When zoomed out, each step is lifted too, per sequence and never across branch boundaries:

1. A step whose relation becomes internal (both ends inside one closed element) is hidden.
2. Consecutive steps in the same sequence that land on the same arrow merge.
3. A branch whose steps are all hidden becomes empty, and a block whose branches are all empty disappears.
4. The remaining steps are renumbered for that level.

## When to use a flow

- For journeys newcomers often ask about: checkout, sign-in, refunds.
- To mark a critical path that must survive refactoring.
- To show the failure path next to the success path, with `alt`.

The full rules are in [specification §12](/referensi/spesifikasi/komposisi-dan-flow/#12-flows).

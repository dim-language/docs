The payments team wants to maintain the gateway model themselves. Move the gateway declaration into `payment.dim` and import it from the main file where the checkout relations are written.

Architecture models grow. Once one file gets hard to read, or several teams write different parts, the model can be split across files. The result is still **one model**: paths, lifting on the map, and relation ids work as if everything were written in one file. All files share one `dim.config`.

The example in this repository is already split that way:

| File | Contents |
|---|---|
| `examples/shop/dim.config` | technologies, tags, and styles for the whole project |
| `examples/shop/shop.dim` | the store system: containers, components, code, and the relations inside it |
| `examples/shop/payment.dim` | the third-party payment gateway, with its API contract |
| `examples/shop/main.dim` | the shopper, relations between systems, flows, and the production environment |
| `examples/shop/to-be.dim` | the next planned architecture, derived from `main.dim` |

## `import`

```dim
// main.dim
dim "0.6";

import "payment.dim";
import "shop.dim";

person customer "Customer" { description "Shops online."; }
clickPay: customer -> shop.web.checkout.button "Click pay" { op use; }
```

An `import` path is relative to the file that writes it, and every file must be in the `dim.config` folder or one of its subfolders. A file imported from several places is loaded only once, and circular imports are rejected.

Two files that both declare `system shop` is an error, just like two sibling elements with the same id. The error message suggests `extend`.

## `extend`

`extend` reopens an element declared in another file to **add** to it:

```dim
// The ops team adds details without changing shop.dim.
extend shop.db { description "One primary instance with one read replica."; tags ops; }
```

Its block is treated as part of the original declaration: properties, members, child elements, relations, even further `extend`s. One limit: in an ordinary file, `extend` can't set a property that's already set (`E605`). Splitting files must never silently change content; to change something, use `amends`.

## `amends` for derived models

Sometimes what you need isn't an addition but **another version** of the same architecture: the current state and the next plan. For that, a file can start with `amends`:

```dim
// to-be.dim
dim "0.6";
amends "main.dim";

extend shop {
  container analytics "Analytics" {
    description "Replaces the nightly report; data arrives through events, not Postgres queries.";
    role database;
    tech clickhouse;
  }

  container events "Checkout Events" {
    description "A queue of checkout events for analytics.";
    role queue;
    tech sqs;
  }
}

extend shop.api {
  tech rust axum08;
  component audit "Audit Log" { … }
}

announceCheckout: shop.api.checkout.service.run -> shop.api.audit.checkoutCompleted { op publish; }
ingestCheckout: shop.analytics -> shop.api.audit.checkoutCompleted { op subscribe; }

remove shop.reports;
```

In an `amends` file, three things that are normally forbidden become allowed:

- `extend` can **override** properties, like `tech` above.
- `unset` removes a property or member, for example `unset external;` for a system that used to be a third party's.
- `remove` deletes an element with all its content, every relation touching it, and every placement of it in environments. `remove` can also delete one relation, flow, flow branch, or environment by its id.

`main.dim` is unchanged and can still be used on its own. Run `dim check to-be.dim` to validate the derived model.

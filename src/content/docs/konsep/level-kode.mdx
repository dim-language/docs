At the deepest level, a model can describe code as fully as a class diagram: which data types exist, which parameters a function needs, what it returns, which errors can happen, and **what each unit is for**. This serves two purposes. An editor can draw class diagrams and call graphs from the same model. And anyone working on the code, human or AI, can read each unit's contract without guessing from its name.

## Paradigms, not programming languages

dim isn't tied to a programming language, but it follows **paradigms**. `class`, `function`, and `record` exist in many languages, while `&Order` or `Result<T, E>` exist in only one. So every container with code states its paradigms:

```dim
container api "API" {
  role service;
  paradigm procedural oop;
  tech rust;
}
```

| Paradigm | Allowed kinds |
|---|---|
| all | `record`, `enum`, `union`, `alias` |
| `procedural` | `module`, `function` |
| `functional` | `module`, `function` (must be `pure` or `effects`) |
| `oop` | `class`, `interface`, `method`, `constructor` |

Multi-paradigm languages such as Rust, Kotlin, or TypeScript just list more than one paradigm. A component can narrow them, for example `paradigm oop;` for a module that only holds classes. A kind outside its paradigms is `E301`, so a `class` can't suddenly appear in a functional service.

## Data types

Types are written as expressions, not strings, with dim's own primitives (`string`, `int`, `decimal`, `uuid`, `datetime`, …), lists `T[]`, optionals `T?`, and `map<K, V>`. Named types are declared as code units and referenced by path:

```dim
alias orderId "OrderId" {
  description "An order id, created at checkout.";
  type uuid;
}

record order "Order" {
  description "An order that's paid and waiting to ship.";
  field id: orderId;
  field items: item[];
  field total: money;
}

enum orderStatus "OrderStatus" {
  description "The stage of an order.";
  variant pending;
  variant paid;
  variant shipped "Handed to the courier";
}
```

Because references go through paths, type names don't have to be unique across the model. A type owned by another component is referenced by its path, such as `payments.paymentError`. Details are in [specification §8](/referensi/spesifikasi/tipe/#8-types).

## The contract: parameters, results, errors

```dim
method run "checkout()" {
  description "One checkout from cart to saved order. The order isn't saved if the charge fails.";
  async;
  param cart: orders.cart "The cart contents and shipping address";
  returns orders.orderId "The id of the new order";
  throws payments.paymentError "The gateway declined the charge";
}
```

- `param <id>: <type> ["<note>"]` can repeat, and its order is the parameter order.
- `returns <type>` appears at most once. Without `returns`, the unit returns nothing.
- `throws <type>` can repeat, one per kind of error. The type must be a `record`, `enum`, `union`, or `class`.
- `field` is used in `record` and `class`, and `variant` in `enum` and `union`.
- `visibility`, `static`, and `abstract` exist only under `oop`. `pure` and `effects` exist only under `functional`.

Members such as `field` and `param` aren't elements: they have no path and can't be relation ends.

## Descriptions are required

Every `module`, `function`, `class`, `interface`, `method`, `constructor`, `record`, `enum`, `union`, and `alias` must have a `description`. Without one, the model doesn't pass (`E205`).

The reason is practical: names like `process()` or `Manager` say nothing. One sentence about a unit's job is the difference between someone (or an AI) using it correctly and guessing. Write what it does and when to use it, not its name again.

```dim
// Not very helpful
description "Repository for orders.";

// More helpful
description "An OrderStore backed by Postgres. Every write uses one transaction per order.";
```

Notes on `field`, `variant`, and `param` are optional.

## Relations between code

Interaction relations work as at other levels. "This method is called by function `x`" is written as `callRun: x -> method { op call; }`. The list of callers is just the arrows coming in.

For the shape of code, there are four **structural** relations:

| `op` | Meaning | Direction |
|---|---|---|
| `inherits` | inheritance | subtype → parent |
| `implements` | fulfilling a contract | class → interface |
| `owns` | composition | owner → owned |
| `refers` | association | holder → referenced |

```dim
repoContract: shop.api.orders.rows -> shop.api.orders.store { op implements; }
```

`inherits` and `implements` exist only under `oop`. Structural relations have no data flow. When zoomed out, they still rise: if a class in component A `inherits` from a class in component B, an `A → B` arrow appears at the component level as a dependency.

## Recursion

Direct recursion is the only relation to itself that's allowed:

```dim
sumBundle: api.checkout.service.total -> api.checkout.service.total "Sum bundle" { op call; }
```

On the map, recursion is drawn as a loop on its box. Indirect recursion (`a → b → a`) is written as two ordinary relations; an editor can detect it as a cycle.

The full rules are in [specification §7](/referensi/spesifikasi/level-kode/#7-code-level).

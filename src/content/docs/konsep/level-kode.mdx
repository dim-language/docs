## Paradigma, bukan bahasa pemrograman

dim tidak terikat ke satu bahasa pemrograman, tapi mengikuti **paradigma**. `class`, `function`, dan `record` ada di banyak bahasa, sedangkan `&Order` atau `Result<T, E>` hanya ada di satu bahasa. Karena itu setiap container yang berisi kode menyatakan paradigmanya:

```dim
container api "API" {
  role service;
  paradigm procedural oop;
  tech rust;
}
```

| Paradigma | Kind yang boleh |
|---|---|
| semua | `record`, `enum`, `union`, `alias` |
| `procedural` | `module`, `function` |
| `functional` | `module`, `function` (wajib `pure` atau `effects`) |
| `oop` | `class`, `interface`, `method`, `constructor` |

Bahasa multi-paradigma seperti Rust, Kotlin, atau TypeScript cukup menulis lebih dari satu paradigma. Component boleh mempersempitnya, misalnya `paradigm oop;` untuk modul yang hanya berisi class. Kind di luar paradigmanya adalah error `E301`, jadi `class` tidak bisa tiba-tiba muncul di service yang fungsional.

## Tipe data

Tipe ditulis sebagai ekspresi, bukan string, dengan primitif milik dim (`string`, `int`, `decimal`, `uuid`, `datetime`, …), list `T[]`, optional `T?`, dan `map<K, V>`. Tipe bernama dideklarasikan sebagai unit kode dan dirujuk lewat path:

```dim
alias orderId "OrderId" {
  description "Id order, dibuat saat checkout.";
  type uuid;
}

record order "Order" {
  description "Order yang sudah dibayar dan menunggu dikirim.";
  field id: orderId;
  field items: item[];
  field total: money;
}

enum orderStatus "OrderStatus" {
  description "Tahap sebuah order.";
  variant pending;
  variant paid;
  variant shipped "Sudah diserahkan ke kurir";
}
```

Karena rujukannya lewat path, nama tipe tidak harus unik di seluruh model. Tipe milik component lain cukup dirujuk dengan path-nya, misalnya `payments.paymentError`. Detailnya ada di [spesifikasi §8](/referensi/spesifikasi/tipe/#8-tipe).

## Kontrak: parameter, hasil, error

```dim
method run "checkout()" {
  description "Satu checkout dari keranjang sampai order tersimpan. Order tidak disimpan kalau penagihan gagal.";
  async;
  param cart: orders.cart "Isi keranjang dan alamat pengiriman";
  returns orders.orderId "Id order yang baru dibuat";
  throws payments.paymentError "Penagihan ditolak gateway";
}
```

- `param <id>: <tipe> ["<keterangan>"]` boleh ditulis berkali-kali, dan urutannya adalah urutan parameter.
- `returns <tipe>` paling banyak satu kali. Tanpa `returns`, unit itu tidak mengembalikan nilai.
- `throws <tipe>` boleh berkali-kali, satu per jenis error. Tipenya harus `record`, `enum`, `union`, atau `class`.
- `field` dipakai di `record` dan `class`, dan `variant` di `enum` dan `union`.
- `visibility`, `static`, dan `abstract` hanya ada di paradigma `oop`. `pure` dan `effects` hanya ada di `functional`.

Member seperti `field` dan `param` bukan elemen: tidak punya path dan tidak bisa menjadi ujung relasi.

## Keterangan itu wajib

Setiap `module`, `function`, `class`, `interface`, `method`, `constructor`, `record`, `enum`, `union`, dan `alias` wajib punya `description`. Tanpa itu, model tidak lolos pemeriksaan (`E205`).

Alasannya praktis: nama seperti `process()` atau `Manager` tidak memberi tahu apa-apa. Satu kalimat tentang tugas sebuah unit adalah perbedaan antara orang (atau AI) yang memakai unit itu dengan benar dan yang menebak. Tulis apa yang dikerjakannya dan kapan dipakai, bukan mengulang namanya.

```dim
// Kurang membantu
description "Repository untuk order.";

// Lebih membantu
description "Implementasi OrderStore di atas Postgres. Semua penulisan memakai satu transaksi per order.";
```

Keterangan di `field`, `variant`, dan `param` opsional.

## Relasi antar kode

Relasi interaksi bekerja seperti di level lain. "Method ini dipanggil oleh function `x`" ditulis sebagai `callRun: x -> method { op call; }`. Daftar pemanggil cukup dihitung dari panah yang masuk.

Untuk bentuk kode, ada empat relasi **struktural**:

| `op` | Arti | Arah |
|---|---|---|
| `inherits` | pewarisan | turunan → induk |
| `implements` | memenuhi kontrak | class → interface |
| `owns` | komposisi | pemilik → yang dimiliki |
| `refers` | asosiasi | yang menyimpan → yang dirujuk |

```dim
repoContract: shop.api.orders.repo -> shop.api.orders.store { op implements; }
```

`inherits` dan `implements` hanya ada di paradigma `oop`. Relasi struktural tidak punya aliran data. Saat di-zoom out, relasi ini tetap naik: kalau class di component A `inherits` class di component B, panah `A → B` muncul di level component sebagai dependency.

## Rekursi

Rekursi langsung adalah satu-satunya relasi ke diri sendiri yang diizinkan:

```dim
sumBundle: api.checkout.service.total -> api.checkout.service.total "Isi bundel" { op call; }
```

Di peta, rekursi digambar sebagai loop di kotaknya. Rekursi tidak langsung (`a → b → a`) ditulis sebagai dua relasi biasa; editor bisa mendeteksinya sebagai siklus.

Aturan lengkapnya ada di [spesifikasi §7](/referensi/spesifikasi/level-kode/#7-level-kode).

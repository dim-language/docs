## “We get the whole order back, right?”

</header>
<img class="dim-scene" src="/brian/order-id.webp" width="640" height="374" alt="" loading="lazy" />
<div class="dim-example-body">

This time Brian asks. His architect shakes her head. “Just the ID.” They pull up **Web App → API** and write that down. Now Brian can give his agent a file that says exactly what goes out (`CheckoutRequest`) and what comes back (`OrderId`).

```dim title="shop.dim"
checkout_post: web.checkout.button -> api.checkout.route "POST /checkout" {
  op call;
  tech "HTTPS/JSON";
  data push "CheckoutRequest";
  data pull "OrderId";
}
```

Brian wrote down the request type. He left out who sends it. CI flags the missing direction with `E035`. The web app sends the request, so Brian adds `push`.

- data "CheckoutRequest";
+ data push "CheckoutRequest";

### When the system gets bigger

- Define [elements](/en/menulis/elemen/) and [relations](/en/menulis/relasi/), then describe [HTTP contracts](/en/konsep/endpoint/) or [code details](/en/konsep/level-kode/) where needed.
- Use a [flow](/en/konsep/alur/) to follow a sequence such as checkout or refunds.
- [Split a model across files](/en/konsep/komposisi/) and [describe proposed changes](/en/konsep/komposisi/#amends-for-derived-models) on top of the current architecture.

In plain C4, each level is a separate diagram drawn on its own. In dim, there's only **one model**. Every zoom level is a view of the same model, computed from which elements are open.

Zoom in to see what's inside each box once it's large enough to read. Double-click `Online Shop` to move closer, then find `API` and go further in.

## Places and regions

Every visible element is in one of two states:

- **A place** (a solid box): an element that's closed, or that has no content. Arrows always attach to places.
- **A region** (a dashed boundary): an element that's open. A region only wraps its content; arrows never attach to it.

The set of places currently visible is called the **frontier**. When every system is closed, the frontier is `Customer`, `Online Shop`, and `Payment Gateway`.

## Lifting

A relation is always stored with its original ends, such as `selectOrder` from `find_by_id()` to `Postgres`. To draw it, each end rises to its nearest ancestor on the frontier:

| Open | `find_by_id()` rises to | `Postgres` rises to | Result |
|---|---|---|---|
| (none) | `Online Shop` | `Online Shop` | not drawn |
| `shop` | `API` | `Postgres` | `API → Postgres` |
| `shop`, `api` | `Orders` | `Postgres` | `Orders → Postgres` |
| everything | `find_by_id()` | `Postgres` | `find_by_id() → Postgres` |

The first row matters: if both ends rise to the same place, the relation is **internal** and isn't drawn. That's why, when `Online Shop` is closed, the relations inside it don't become an arrow from `Online Shop` to itself.

It's also why dim forbids a relation between an element and its own ancestor (error `E404`): such a relation would disappear at every zoom level.

## Aggregation

Several relations can rise to the same pair of places. When `API` and `Postgres` are visible as boxes, `insertOrder`, `selectOrder`, and `recordRefund` all show as `API → Postgres`. They merge into one arrow that still carries:

- the ids of its source relations, so it can be traced back;
- every `op` involved (`write, read`);
- the data flow per direction (`push Order, RefundId` and `pull Order`).

Direction is respected: `a → b` and `b → a` are two different arrows.

Open **Relations in this view** below the map to see the result of aggregation. Choose a relation to highlight its arrow and see the operations and data that flow.

## Who does what

The parser does **not** lift. A parsed model always contains relations with their original ends, and the view computes the frontier, lifting, and aggregation. That way one JSON file is enough for every zoom level, and every view draws the same diagram from the same model.

The normative rules are in [specification §14](/en/referensi/spesifikasi/semantik-zoom/#14-zoom-semantics-lifting). The deployment view, which applies the same rules to the node hierarchy, is covered in [Map where software runs](/en/konsep/deployment/).

## Check the result

Choose the arrow from API to Postgres while both are visible as boxes. Zoom into API until `find_by_id()` appears. Confirm that the `selectOrder` arrow now starts at `find_by_id()`, with the same `SELECT orders` label.

The Web app needs an order id after checkout. Look at the POST call in the Web code, then note what the Web app sends and what it uses from the response.

Every relation in dim answers two different questions:

1. **Who starts?** Answered by the direction of the `->` arrow.
2. **What data flows, and which way?** Answered by `data`.

## The arrow: who starts

An arrow always points from whoever starts the interaction to its target.

```dim
selectOrder: shop.api.orders.rows.find -> shop.db "SELECT orders" { op read; }
```

`rows.find` asks the database, so the arrow starts at `rows.find`. That's also the direction of the dependency: `rows.find` depends on `db`, not the other way around.

## `data`: what flows

The direction of data is written from the initiator's point of view, followed by its type:

| Direction | Meaning | Relative to the arrow |
|---|---|---|
| `push` | the initiator sends data to the target | with it |
| `pull` | the initiator fetches data from the target | against it |

```dim
selectOrder: shop.api.orders.rows.find -> shop.db "SELECT orders" {
  op read;
  data pull shop.api.orders.order;
}
```

The direction is **always written**, and it must fit the `op`:

| `op` | Allowed directions |
|---|---|
| `read`, `subscribe` | `pull` |
| `write`, `publish` | `push` |
| `call`, `use` | `push`, `pull`, or both |

A single call usually moves data both ways: a request goes out, a response comes back. So `data` can be written more than once:

```dim
runCheckout: shop.api.checkout.route -> shop.api.checkout.service.run "Run checkout" {
  op call;
  data push shop.api.orders.cart;
  data pull shop.api.orders.orderId;
}
```

The type in `data` is a dim type expression that refers to a named type, such as a `record` or an `alias`, by path, so the map can open the type's definition straight from the arrow. See [Record a function contract](/en/konsep/level-kode/).

## Relations to endpoints don't write data

When the target is an endpoint, the data is already in the endpoint's contract. The relation is just:

```dim
postCheckout: shop.web.checkout.button -> shop.api.checkout.post { op call; }
```

`push` comes from `body`, and `pull` from `returns`. Writing `data` on such a relation is `E406`, so the contract lives in one place only. See [Document an endpoint](/en/konsep/endpoint/).

## Why not use the arrow for data?

- A `call` moves data both ways, and one arrow has only one direction.
- If the arrow followed the data, an `api` that reads a `db` would be drawn `db → api`, even though `api` depends on `db`. When zoomed out, the direction of dependency would mix with the direction of data.
- `push` and `pull` read directly, without memorizing what symbols like `=>` or `<-` mean.

## When zoomed out

Data flows rise with their relations. On the [zoom map](/en/konsep/peta-zoom/), the `API → Postgres` arrow carries `push Order` and `pull Order`, because inside it one function writes and one reads. The full rules are in [specification §9.5](/en/referensi/spesifikasi/relasi/#95-data-flow).
